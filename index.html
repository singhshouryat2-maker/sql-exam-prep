Key ideas

If you know these 12, you can answer most questions.

Sargable filter

An index on a column only helps if the column is left alone in the WHERE. DATE(departure_at) = '2026-07-05' wraps it in a function, so no index. Write a range instead: departure_at >= '2026-07-05 00:00+05:30' AND departure_at < '2026-07-06 00:00+05:30'. Used in R01, R02, R12, R20.

NOT IN vs NOT EXISTS

If the subquery returns even one NULL, x NOT IN (…) is never true, so you get 0 rows. R13 gave 0 unused coupons. NOT EXISTS ignores NULLs and gave the correct 10.

Correlated subquery

A subquery that uses a column from the outer row runs once per outer row. In R19 it ran 720 times (2,150 ms). One LEFT JOIN … GROUP BY did the same in 20 ms (105× faster).

Composite index

Column order matters. Put equality columns first and the range column last: (customer_id, status), (origin, destination, departure_at). It works for filters on the leftmost columns, not for the second column alone.

Partial index

It indexes only the rows that match a WHERE, so it's tiny when that set is small: WHERE status = 'DELAYED' (R10), 'PENDING_PAYMENT' (R11, W02), age >= 60 (R21). A query must use the same condition to use it.

Expression index

It indexes the result of an expression. ON customers (lower(email)) lets R23 (case-insensitive sign-in) use an index: 14.4 ms → 0.07 ms.

Covering index (INCLUDE)

ON flight_bookings (flight_id) INCLUDE (passengers) stores the extra column in the index, so PostgreSQL can answer from the index alone. The plan shows an Index Only Scan.

Foreign keys aren't indexed automatically

PostgreSQL indexes PRIMARY KEY and UNIQUE columns, but not foreign keys. flight_bookings.flight_id and hotel_reviews.hotel_id needed their own indexes (R01, R07, R24).

When an index can't help

A query that reads most of a table (R14, R16: every booking), a leading wildcard ILIKE '%breakfast%' (R18: needs a pg_trgm GIN index), or a column-vs-column test departure_at - booked_at < 24h (R25).

OFFSET vs keyset paging

OFFSET 100000 LIMIT 25 still reads 100,025 rows. Keyset paging jumps straight there: WHERE booked_at < :last_seen ORDER BY booked_at DESC LIMIT 25 (R22).

Write overhead

Each index must be updated on every INSERT/UPDATE. W01 barely changed (1.18 → 1.09 ms), W03 got a little slower (0.39 → 0.50 ms), and W02 got much faster because finding the row became cheap.

Planner statistics

The planner picks a plan from its row guesses. On the large data, R03 guessed 14 Goa pool hotels when there were 1,920, so it picked a slow plan. Fix: ANALYZE, and CREATE STATISTICS on the JSON expression.

Scenario questions

Try to answer each one in your head or on paper first, then open the model answer.

1. Reports for June 2026 are slow

SELECT count(*) FROM bookings
WHERE EXTRACT(MONTH FROM booked_at) = 6
  AND EXTRACT(YEAR FROM booked_at) = 2026;

There is an index on booked_at, but the plan shows a Seq Scan. Why, and how do you fix it?

Show answer

EXTRACT wraps the column in a function, so the filter is not sargable and the index can't be used. Rewrite it as a range on the bare column:

SELECT count(*) FROM bookings
WHERE booked_at >= '2026-06-01 00:00+05:30'
  AND booked_at <  '2026-07-01 00:00+05:30';

Use >= start and < next start, not BETWEEN with 23:59:59. The +05:30 keeps the same IST days as the original. This is what we did for R12 and R20.

2. Marketing says the report shows 0 unused coupons, but they know some are unused

SELECT coupon_code FROM coupons
WHERE coupon_code NOT IN (SELECT coupon_code FROM bookings);
Show answer

Most bookings have no coupon, so bookings.coupon_code contains NULL. x NOT IN (…, NULL) evaluates to UNKNOWN, never TRUE, so every coupon is filtered out. Fix it with NOT EXISTS (or add WHERE coupon_code IS NOT NULL to the subquery):

SELECT c.coupon_code FROM coupons c
WHERE NOT EXISTS (SELECT 1 FROM bookings b
                  WHERE b.coupon_code = c.coupon_code);

This returns the correct 10 rows. The partial index ON bookings (coupon_code) WHERE coupon_code IS NOT NULL makes it an anti-join with an index-only scan (35.8 → 0.16 ms).

3. Write a query: top 5 customers by spend in 2026, excluding cancelled bookings. Which index helps?

Show answer
SELECT customer_id, count(*) AS bookings, sum(total_amount) AS spend
FROM bookings
WHERE status <> 'CANCELLED'
  AND booked_at >= '2026-01-01 00:00+05:30'
  AND booked_at <  '2027-01-01 00:00+05:30'
GROUP BY customer_id
ORDER BY spend DESC
LIMIT 5;

Index: bookings (booked_at) (our idx_bookings_booked_at) for the date range. But a whole year is a large share of the table (about a third of all bookings), so the gain is small. Like R12 and R17, reading many rows is unavoidable. For a dashboard you'd use a materialized view refreshed nightly.

4. Find flights in July 2026 that have no bookings at all

Show answer
SELECT f.flight_id, f.flight_no, f.departure_at
FROM flights f
WHERE f.departure_at >= '2026-07-01 00:00+05:30'
  AND f.departure_at <  '2026-08-01 00:00+05:30'
  AND NOT EXISTS (SELECT 1 FROM flight_bookings fb
                  WHERE fb.flight_id = f.flight_id);

Same idea as a LEFT JOIN … WHERE fb.flight_id IS NULL. Avoid NOT IN. Indexes: idx_flights_departure for the date range and idx_fb_flight on the foreign key for each lookup. R08 is the version with fewer than 5 passengers: it uses LEFT JOIN + HAVING coalesce(sum(fb.passengers),0) < 5, so flights with zero bookings still appear.

5. The support console is slow on page 4,001 and gets slower the further you go

SELECT * FROM bookings ORDER BY booked_at DESC OFFSET 100000 LIMIT 25;
Show answer

OFFSET still reads and throws away every skipped row. Before our fix it sorted all bookings on disk (8 MB external merge, 82 ms). The booked_at index removed the sort (Index Scan Backward, 20 ms), but it still reads 100,025 rows. The real fix is keyset pagination: the app remembers the last booked_at it showed.

SELECT * FROM bookings
WHERE booked_at < :last_seen_booked_at
ORDER BY booked_at DESC
LIMIT 25;

That reads only 25 rows on any page. If two bookings can share a timestamp, add booking_id as a tie-breaker: WHERE (booked_at, booking_id) < (:t, :id) ORDER BY booked_at DESC, booking_id DESC.

6. After the data grew 20×, a query that took 0.8 ms now takes 8 ms. How do you find out why?

Show answer

1) Run EXPLAIN (ANALYZE, BUFFERS). 2) Compare estimated rows with actual rows at each step. 3) Look for Rows Removed by Filter, sorts and loops.

This was R03 for us: the planner guessed 14 hotels with a pool but found 1,920, so it fetched all 2,740 Goa 4★+ hotels and sorted them. Fix: an index in the ORDER BY order, (city_name, user_rating DESC NULLS LAST), plus CREATE STATISTICS … ON ((amenities ->> 'pool')) so the guess is right. It now reads 83 rows and stops: 8.1 → 0.33 ms.

7. Show bookings per day in June 2026 with a running total

Show answer
SELECT day, bookings,
       sum(bookings) OVER (ORDER BY day) AS running_total
FROM (
  SELECT (booked_at AT TIME ZONE 'Asia/Kolkata')::date AS day, count(*) AS bookings
  FROM bookings
  WHERE booked_at >= '2026-06-01 00:00+05:30'
    AND booked_at <  '2026-07-01 00:00+05:30'
  GROUP BY 1
) d
ORDER BY day;

A window function with OVER (ORDER BY day) adds up all rows up to the current one without collapsing them. Filter with a range, not booked_at::date BETWEEN, so the index works. That gave an index-only scan in R20 (13.2 → 2.9 ms).

8. Should we partition the bookings table?

Show answer

We tested RANGE partitioning by booked_at per quarter on 2.9 M bookings (08_partitioning.sql). Pruning worked: the June query read only bookings_2026_q2. But it was not faster (22.0 vs 21.4 ms), because the booked_at index already finds the rows.

Partitioning helps with archiving (drop a whole quarter instantly instead of a slow DELETE), smaller per-partition indexes, and per-partition VACUUM. The cost: the primary key must include the partition key, (booking_id, booked_at). Decision: not yet, only at about 50–100 M rows or when old data must be archived.

Exam tips

  • For "why is this slow", check: a function on the column? A leading %? A missing foreign-key index? A correlated subquery? A big OFFSET? NOT IN with NULLs?
  • For "which index", put equality columns first and the range column last. Use a partial index for a rare status, an expression index for lower(), and INCLUDE to make it covering.
  • Say when an index won't help: when a query reads most of the table, the answer is "no index helps; use a summary or materialized view".
  • Always state the trade-off: more indexes mean faster reads, slower writes and more disk (our indexes are 748 MB on the large data, almost the table size of 776 MB).
  • Use your own numbers. They show you did the work: R19 2,150 → 20 ms, R13 0 → 10 rows, R03 8.1 → 0.33 ms at 20× data, and 5.7× faster in total.
